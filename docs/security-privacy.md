# Privacy and security by design

Status: decided 2026-11-04, with the move from Docusaurus to Astro. Review again before the application form and reviewer evaluation go live.

This note covers two systems:

1. **The public site** (gh27.bat.or.th): event information and aggregate data. It exists today.
2. **The application and review portal**: applicants apply, and reviewers score applications. It is planned.

They have very different risks, so they are built and deployed separately.

## 1. Principles

These follow PDPA (Thailand's Personal Data Protection Act B.E. 2562) and the privacy-by-design principles behind it.

- **Collect less.** Every personal field needs a reason tied to selecting participants or running the event. A field with no reason is not collected.
- **Keep it apart.** The public site never touches personal data. The portal never touches genomic data. Genomic analysis stays inside NSTDA's Secure Data Environment (see `CLAUDE.md`).
- **Deny by default.** Every portal route needs a signed-in user with the right role. Public is the exception, and it is declared explicitly.
- **Delete on schedule.** Personal data has a stated retention period and is deleted when it ends.
- **No third parties without a reason.** No analytics, trackers, ad pixels or third-party embeds. A third party that does see personal data needs a data processing agreement.

## 2. The public site (this repository)

The site is static HTML built by Astro and served by GitHub Pages. There is no server code, database, login or cookie, so most web attack classes do not apply. What remains:

| Risk | Control in this repo |
|---|---|
| Visitors' IP addresses sent to Google by Google Fonts | Inter Tight is self-hosted from `@fontsource/inter-tight`. The page loads nothing from other origins. |
| Script injection, or a compromised dependency calling home | A Content Security Policy with script and style hashes is generated by Astro. No `unsafe-inline` or `unsafe-eval` for scripts, no inline event handlers, and `connect-src` is `'self'` only. Inline `style` attributes are allowed (React and the barcode use them); they can restyle the page but not run code. |
| Clickjacking, MIME sniffing, referrer leaks | `referrer` policy `strict-origin-when-cross-origin`. External links use `rel="noopener noreferrer"`. GitHub Pages cannot set response headers, so `frame-ancestors` and `X-Content-Type-Options` need the Cloudflare proxy (see §5). |
| Personal or sensitive data published by mistake | Only aggregate project counts are published (`data/wgs_projects.tsv`). `appendix/` stays git-ignored. Site tests fail if an email address or phone number appears in the built HTML. |
| Visitor tracking | None. The colour theme is kept in `localStorage` on the visitor's device and never sent anywhere. |
| Supply chain | `npm ci` from the lockfile and few dependencies. The deploy workflow has only the permissions Pages needs. Turn on Dependabot alerts in the repository settings. |

## 3. The application and review portal (planned)

### 3.1 Where it lives

- **A separate deployment** on its own subdomain, for example `apply.gh27.bat.or.th`. A bug in the public site cannot reach applicant data, and the public site stays static.
- **Astro in server mode** (`output: 'server'` with the Node adapter), sharing the design tokens in `src/css/custom.css`. Use Astro Actions with zod schemas for every form post, Astro sessions, and middleware for authorisation.
- **Hosted in Thailand**, or in a region covered by an approved cross-border transfer basis (PDPA s.28–29). The faculty's or BAT's own infrastructure is preferred over a foreign SaaS.
- **PostgreSQL** with encryption at rest, TLS in transit, backups that are encrypted too, and no public network access to the database.

### 3.2 What to collect

The current Google Form (`tools/google-form/create-application-form.gs`) asks for more than selection needs. Proposed changes for the portal:

| Field in the current form | Proposal | Reason |
|---|---|---|
| Date of birth | Replace with "I am 18 or older" (yes/no) | Age is not a selection criterion |
| Title / prefix | Drop | Not needed |
| Full name (Thai) | Optional | Needed only for certificates |
| Nationality (free text) | "I am a Thai national" (yes/no) | Eligibility is yes or no. Check identity at NDA signing, not in the form |
| Phone number, LINE ID | Ask only after acceptance | Needed only for accepted participants |
| Flight, province, accommodation | Ask only after acceptance | Logistics, not selection |
| Typed "signature" and date | Replace with a recorded consent (who, when, which version of the terms) | A typed name proves nothing; the record does |
| GCP certificate file | Yes/no plus expiry date. Collect the file after acceptance, if at all | Avoid storing identity documents for everyone who applies |

Never collect: national ID or passport numbers, health information, religion, or anything else that is sensitive data under PDPA s.26.

Before the form, show a privacy notice: who controls the data (Faculty of Medicine, Chiang Mai University), the purpose, the legal basis (consent for applying, contract for accepted participants), who sees it, how long it is kept, the data subject's rights and how to use them, and the DPO's contact details.

### 3.3 Who sees what

| Role | Can see | Cannot see |
|---|---|---|
| Applicant | Their own application and its status | Anyone else's data, scores or reviewer names |
| Reviewer | Applications assigned to them, with name, email and institution hidden (blind review) | Unassigned applications, other reviewers' scores before they submit their own |
| Committee chair | All applications and scores; can assign reviewers and record decisions | Nothing extra is needed |
| Administrator | Accounts, roles and exports | Scores are read-only for them |

- Reviewers declare conflicts of interest for each assignment. A conflict blocks the assignment.
- Scores use a fixed rubric based on the selection criteria in `src/data/event.ts`, with a comment for each score.
- Every read of an application and every change of a score or decision goes to an append-only audit log.
- Exports are limited to the chair, pseudonymised by default, and logged.

### 3.4 Sign-in and sessions

- Applicants sign in with an emailed one-time link or code: no password to store or leak.
- Reviewers and staff sign in through the institution's single sign-on (OIDC), with multi-factor authentication required.
- Session cookies are `HttpOnly`, `Secure`, `SameSite=Lax` and host-only. Sessions end after 30 minutes idle for reviewers and staff.
- Rate-limit sign-in and submission. Use a privacy-friendly challenge only if abuse appears.

### 3.5 Secure by design checklist for the portal

- Validate every input on the server with a zod schema and a maximum length; never trust client checks.
- Parameterised queries only (an ORM or query builder); row-level checks on every query that takes an application id.
- Same-origin checks on all state-changing requests (Astro's `security.checkOrigin`).
- Strict CSP and security headers from middleware, the same baseline as the public site.
- Uploads, if any: size and type limits, stored outside the web root, served only to authorised roles, scanned.
- Secrets in the host's secret store, never in the repository. Separate credentials per environment.
- No personal data in logs, URLs, error messages or analytics.
- Test the access rules: an automated test per role that tries to read another user's application.

### 3.6 Retention

| Data | Kept until |
|---|---|
| Applications that were not accepted | 6 months after participants are announced (July 2027), then deleted |
| Accepted participants' records | 1 year after the event, or as the NDA, DUA and ethics approval require |
| Reviewer scores and comments | Deleted with the application; aggregate statistics may be kept |
| Audit log | 2 years |

A scheduled job does the deletion and records that it ran.

## 5. Hosting follow-up for the public site

DNS is a Cloudflare CNAME to GitHub Pages. Turning on the Cloudflare proxy would let a Transform Rule add the headers GitHub Pages cannot set: `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: frame-ancestors 'none'` and `Permissions-Policy`. This is an account change for whoever runs the Cloudflare zone.
